# 개발 계획

- MVP 먼저 내고, 검색 알고리즘은 STORIX-AI 만 따로 배포해서 개선한다. 앱 · Spring 은 API 계약만 지키면 된다
- 알고리즘을 바꿀 때마다 같은 평가 세트로 숫자를 비교하고 나아졌을 때만 배포한다
- 0~2단계까지 개발하고, 3단계부터는 사용자 유즈케이스를 보고 정한다

## 1. 단계

| 단계 | 목표 | 범위 |
| --- | --- | --- |
| 0. 준비 | 같이 일할 수 있는 바닥 | API 계약, mock API, 레포 · 배포 경로, 평가 세트 초안 |
| 1. MVP | 대화로 작품 5개 추천이 끝까지 동작 | 작품 DB 기반 검색, 조건 추출, 스트리밍 답변, 대화 저장, 범위 밖 · 19금 처리 |
| 2. 알고리즘 v2 | 검색 품질 올리기 | 표지 라벨, UGC 색인, 재순위, 지난 대화 요약 |
| 3. 확장 | 쓰임새 넓히기 | 그림체 비슷한 작품, 외부 서칭, 에이전트 비서 · 먼저 추천 알림 |

## 2. 기술 스택

| 영역 | 기술 | 비고 |
| --- | --- | --- |
| 앱 | 기존 STORIX 앱 | AI 검색 화면, POST 스트리밍(SSE) 수신 |
| 백엔드 | Java 17 · Spring Boot 3.5 (STORIX-BE) | 인증 · 사용 횟수 · 대화 저장 · 결과 검증. AI 서버 호출은 WebClient |
| AI 서버 | Python 3.12 · FastAPI · uvicorn · Pydantic | 패키지는 uv, 테스트는 pytest |
| LLM | Claude Haiku (조건 추출 · 분류) + Claude Sonnet (답변) | Anthropic Python SDK. tool use 로 작품 ID 만 받음, 프롬프트 캐싱 |
| 임베딩 | 한국어 지원 임베딩 모델 1개 (미정) | 후보: bge-m3 · multilingual-e5 계열(로컬, 0원) 또는 유료 API. 서버 메모리에 들어가는 크기로 결정 |
| 검색 | Elasticsearch 8.18 (기존, nori) | `dense_vector` kNN + BM25 하이브리드, 필터 |
| 저장소 | MySQL(RDS) · Redis (기존) | 대화 기록 · 설정은 MySQL, 진행 중 대화 캐시는 Redis |
| 색인 배치 | Python 스크립트 (`indexing/`) | 작품 적재 시 바로 색인. v2 부터 표지 라벨용 로컬 VLM |
| 배포 | Docker · GitHub Actions · ECR (기존 방식) | 앱 서버 내부 네트워크에만 붙임. 인터넷에 열지 않음 |
| 모니터링 | Prometheus · Grafana · Loki (기존) | 응답 시간, 답변당 토큰 · 비용, 오류율 |

## 4. 정해진 정책

| 정책 | 구현 위치 |
| --- | --- |
| 추천 카드 최대 5개 | ⑦ 답변 도구 스키마 · Spring 검증 |
| 범위 밖 질문(사담 · 날씨 · 프롬프트 조작)은 통일된 고정 문구 | ① 조건 추출에서 분류 → 서버 고정 문구 |
| 미성년자는 성인 작품 추천 안 함, 성인은 설정으로 켜고 끔 | ② 필수 필터. 성인 인증 여부는 Spring 이 판단해 전달 |
| 말투는 ~해요체 | `prompts/system.md` |
| 서재 작품 제외, 관심작품과 비슷한 작품은 추천 가능 | ② 필수 필터 · 내부 API |
| 대화는 대화방 단위, 탈퇴 시까지 보관. 모델은 최근 25개만 읽고 이전은 요약 | MVP: 최근 25개 / v2: 요약 · 색인 |
| 새 작품은 적재될 때 바로 반영 | 작품 적재 연동 → `/internal/index/works` |
| 사용 횟수 제한은 우선 없음 | Spring 에 자리만 만들어 두고 끔. 비용 지표는 수집 |
| 구축 방식 문서화 (약관 업데이트 대비) | 사용 데이터 · 외부 전송 항목 정리 문서 |

## 5. 단계별 할 일

### 0단계. 준비

- API 계약 확정: 요청 · 응답 · SSE 이벤트 · 오류 코드 (`schemas/`)
- mock API: 고정 응답을 SSE 로 흘려주는 API. 앱은 이걸로 화면을 먼저 끝까지 만듦
- 레포 · CI · Docker 이미지 · 앱 서버 내부 네트워크 배포 경로
- 임베딩 모델 결정: 서버 메모리 · 한국어 품질 · 속도로 후보 2~3개 비교
- 평가 세트 초안: 질문 → 정답 작품 50~100개, 범위 밖 · 탈옥 · 19금 우회 질문 포함
- 화면 · 대화 흐름 디자인: 카테고리 선택, 예시 질문, 진행 표시, 카드, 오류

### 1단계. MVP

| 영역 | 할 일 |
| --- | --- |
| AI 서버 | 작품 DB(설명 · 태그 · 장르) 색인 배치와 `works_ai`, ① 조건 추출, ② 필터 + ③ 하이브리드 검색, ⑦ 답변(Sonnet · ~해요체 · 최대 5개 · `recommend_works`), Claude 스트림 → SSE 변환, 범위 밖 · 결과 없음 고정 문구, 작품 색인 · 삭제 내부 API |
| 백엔드 | `aichat` 도메인 · 마이그레이션, 앱 API 4종(진입 · 지난 대화 · 질문 · 설정) · SSE 전달, 작품 ID 검증 · 카드 정보 채우기 · 서재 제외, 미성년자 · 19금 설정 반영, 사용자 맥락 내부 API · 서비스 토큰, 작품 적재 때 색인 요청, 스트리밍 동안 DB 커넥션 안 잡기 |
| 앱 | AI 검색 화면 · 진입 경로(홈 플로팅 버튼 · 검색 상세), 카테고리 선택 · 예시 질문, POST 스트리밍 수신 · 카드 5개 · 오류 화면, 지난 대화 목록 · 19금 추천 설정 |
| 평가 · 출시 조건 | Recall@10 · 추천 Precision, 조건 추출 정확도, 성인 노출 0건 · 범위 밖 차단, 응답 시간 · 답변당 비용, 사용 데이터 · 외부 전송 항목 문서화 |

### 2단계. 알고리즘 v2 (STORIX-AI 단독 배포)

- 표지 라벨링: 로컬 VLM 으로 1,000개 먼저 → 품질 확인 후 전체
- 공개 UGC 색인 (리뷰 → 피드 → 토픽룸), 삭제 · 비공개 반영
- ④ 후보 묶기, ⑤ 재순위, ⑥ 근거 검증 강화(단서 출처, 스포일러)
- 25개 이전 대화 요약 · 색인
- 단계마다 평가 세트 숫자 비교 후 배포, `pipeline_version` 기록

### 3단계. 확장

- SigLIP 이미지 벡터로 작품 상세 "그림체 비슷한 작품"
- 외부 서칭 (예: "리디 블프 작품 추천해줘")
- 에이전트 비서: 지난 대화 바탕 다음 날 리포트, 주말 · 연휴 먼저 추천 알림
- 사용 횟수 제한 (비용 지표를 보고 결정)

## 6. 기대 결과와 기준

### MVP: 작품 설명 · 태그 · 장르에 적힌 것까지

| 잘 되는 질문 | 되는 이유 |
| --- | --- |
| "회귀 복수물 판타지 웹소설" | 장르 · 소재가 설명과 태그에 있음 |
| "계약결혼 로판 중에 완결된 거" | 소재는 검색, 완결은 필터로 정확히 거름 |
| "집착남 나오는 거" ≈ "집착 남주" | 임베딩이 비슷한 표현을 같은 뜻으로 묶음 |
| "카카오페이지 웹툰만", "19금 빼고" | 필터라서 반드시 지켜짐 |
| "그거 말고 완결된 걸로" | 최근 25개 대화와 이미 보여 준 작품을 기억함 |

| 약한 질문 | 약한 이유 | 채우는 단계 |
| --- | --- | --- |
| "은발 꼬마랑 흑발 아빠 나오는 거" | 외형은 설명에 잘 안 적힘 | v2 표지 라벨 |
| "고구마 없는 사이다물", "전개 빠른 거" | 독자 평가라 설명에 없음 | v2 리뷰 · UGC 색인 |
| "그림체 예쁜", "파스텔톤" | 그림 정보가 없음 | 3단계 SigLIP |
| "주인공이 기억 잃고 시작하는 그 작품 뭐였지" | 설명이 짧으면 못 찾음 | v2 UGC 일부 |
| "요즘 핫한 거" | 인기 지표를 안 씀 | v2 재순위 + 인기 점수 |

| 속도 · 비용 (추정) | 예상 | 근거 |
| --- | --- | --- |
| 진행 표시 | 바로 | 요청 받자마자 progress 이벤트 |
| 첫 글자 | 2~3초 | 조건 추출(Haiku) 0.5~1초 + 임베딩 · 검색 0.1~0.3초 + Sonnet 첫 토큰 1~2초 |
| 답변 끝 + 카드 5개 | 5~10초 | 답변 길이에 따라 다름 |
| 비용 | 답변당 몇 센트 이내 | 후보 20개(입력 3~4천 토큰) + 짧은 답변, 프롬프트 캐싱으로 감소 |

| MVP 출시 기준 (제안) | 목표 |
| --- | --- |
| 장르 · 소재 · 조건 질문 | Recall@10 70% 이상, Precision@5 60% 이상 |
| 외형 · 분위기 · 독자 평가 질문 | 측정만, v2 기준선 |
| 정책 (지어낸 작품, 성인 노출) | 0건 |
| 범위 밖 질문 차단 | 95% 이상 |

### v2: 표지 · 리뷰 · 인기 반응까지

| 좋아지는 질문 | 이유 | 추가 기능 |
| --- | --- | --- |
| "은발 꼬마랑 흑발 아빠 나오는 거" | 표지 외형 · 의상이 검색 대상에 들어감 | 표지 라벨 (VLM) |
| "고구마 없는 사이다물", "전개 빠른 거" | 리뷰에 적힌 독자 평가로 찾음 | 리뷰 · UGC 색인 |
| "주인공이 기억 잃고 시작하는 그 작품 뭐였지" | 리뷰 · 피드에 적힌 줄거리로 찾음 | UGC 색인 |
| "요즘 핫한 로판" | 관심작품 수 · 최근 반응을 점수에 섞음 | 재순위 + 인기 점수 |
| "A 랑 비슷한데 더 가벼운 거" | 조건 일치율로 후보를 다시 정렬 | 재순위 |
| "어제 얘기한 거 이어서" | 25개 이전 대화도 요약으로 기억 | 지난 대화 요약 · 색인 |

| 카드 변화 | MVP | v2 |
| --- | --- | --- |
| 일치한 단서 | 설명 · 태그에서 나온 것만 | 표지 · 리뷰 · 피드까지, 출처 표시 (COVER · REVIEW 등) |
| 스포일러 | 프롬프트 규칙으로만 막음 | 근거 검증 단계에서 결말 언급 걸러냄 |
| 같은 작품 중복 | 작품당 문서 1개라 없음 | 여러 리뷰가 같은 작품을 가리켜도 하나로 묶음 |

v2 에서도 약한 질문: "그림체 예쁜" · "파스텔톤"(3단계 SigLIP), 막 올라온 작품(설명 · 표지 라벨로만), 리뷰가 적은 작품(데이터가 쌓이면 나아짐), 특정 회차 장면(범위 밖)

| 속도 · 비용 · 인프라 (추정) | 변화 | 근거 |
| --- | --- | --- |
| 첫 글자 | +0.3~1초 | 재순위 단계 추가. CPU 재순위 모델이면 더 늘어남 |
| 답변당 비용 | +20~40% | 단서가 늘어 입력 토큰 증가. 캐싱으로 일부 상쇄 |
| ES 메모리 | 크게 늘어남 | UGC 를 따로 색인하면 문서 · 벡터가 작품 수의 수십 배. 지금 ES 1GB 로는 부족할 가능성 큼 |
| 표지 라벨링 | 로컬 VLM 이면 0원, 시간이 듦 | 작품 수 × 표지당 수 초. 1,000개로 먼저 확인 |
| UGC 외부 전송 | 개인정보 처리방침 확인 | 작성자 ID · 닉네임은 빼고 본문만 |

진행 순서(제안): 재순위 + 인기 점수(새 데이터 없이 바로 효과) → 표지 라벨(외형 질문 체감이 큼) → 리뷰 색인(ES 메모리 먼저 확인) → 피드 · 토픽룸 색인(비용 · 메모리 본 뒤) → 지난 대화 요약(실사용 긴 대화 비율 보고)

| v2 배포 기준 (제안) | 목표 |
| --- | --- |
| 외형 · 분위기 · 독자 평가 질문 | MVP 기준선 대비 Recall@10 이 오를 때만 |
| 장르 · 소재 · 조건 질문 | MVP 대비 떨어지지 않음 |
| 정책 (지어낸 작품, 성인 노출) | 0건 유지 |
| 단서 출처 정확도 | 표시한 출처에 실제로 그 내용이 있음 90% 이상 |
| 첫 글자 시간 · 답변당 비용 | MVP 대비 +1초 · +40% 이내 |

### 3단계: 검색창 밖으로 넓히기

| 기능 | 보이는 곳 | 필요한 것 | 한계 |
| --- | --- | --- | --- |
| 그림체 비슷한 작품 | 작품 상세 | SigLIP 이미지 벡터 (배치). 응답 0.1초 안팎 | 표지 1장 기준이라 본편 그림체와 다를 수 있음 |
| 분위기 · 색감 질문 | AI 검색 | SigLIP 텍스트 인코더 상시 탑재 (서버 메모리 증가) | 한국어에 약해서 평가 세트로 효과 확인 후 |
| 다음 날 리포트 | 알림 → AI 검색 | 사용자별 장기 취향 저장, 하루 1번 배치 | 대화를 안 한 사용자에게는 보낼 내용이 없음 |
| 먼저 추천 알림 | 푸시 알림 | 장기 취향 + 발송 정책 | 너무 자주 보내면 알림을 꺼 버림 |
| 사용 횟수 제한 | AI 검색 | 1 · 2단계에서 모은 비용 지표 | - |

- 주의: 먼저 추천은 광고성 정보라 마케팅 수신 동의자에게만, 야간(21시~08시)은 별도 동의. 장기 취향 저장은 개인정보 처리방침 · 보관 기간에 반영. 알림은 주 1~2회 상한 · 끄기 · 빈도 설정. 그림체 벡터도 표지 수집 방식 · 플랫폼 약관 점검 대상
- 리포트 · 먼저 추천 비용은 대상자 수 × 하루 1번. 최근 활동 사용자로 대상 제한
- 진행 순서(제안): 그림체 비슷한 작품 → 사용 횟수 제한(비서 기능 전에 비용 상한) → 다음 날 리포트 → 먼저 추천 알림. 분위기 · 색감 질문은 평가 세트에서 효과가 확인될 때만

| 3단계 배포 기준 (제안) | 목표 |
| --- | --- |
| 그림체 비슷한 작품 | 사람이 보고 "비슷하다"고 한 비율 70% 이상 (작품 50개 샘플) |
| 리포트 · 먼저 추천 | 알림 열람률이 기존 마케팅 알림보다 높음 |
| 알림 끄기 비율 | 기존 마케팅 알림보다 늘지 않음 |
| 정책 | 미동의자 · 야간 발송 0건, 미성년자 성인 작품 0건 유지 |
| 비용 | 사용자당 하루 비용 상한 안에서 운영 |

## 7. 평가 지표

| 구분 | 지표 | 보는 것 |
| --- | --- | --- |
| 사전 (평가 세트) | Recall@10 | 정답 작품이 후보 안에 들어왔나 |
| 사전 | 추천 Precision@5 | 추천한 5개 중 맞는 비율 |
| 사전 | 후보 밖 작품 비율 | 없는 작품을 지어냈나 (목표 0%) |
| 사전 | 조건 추출 정확도 | 질문에서 조건을 맞게 뽑았나 |
| 사전 | 범위 밖 차단율 · 성인 노출 | 정책을 지키나 (성인 노출 0건) |
| 사후 (실사용) | 카드 클릭률 · 관심작품 추가율 (GA) | 추천이 쓸모 있었나 |
| 사후 | 대화당 다시 묻는 횟수 | 한 번에 찾았나 |
| 사후 | 첫 글자 · 전체 응답 시간, 답변당 토큰 · 비용 | 기다릴 만한가, 예산 안인가 |

- 평가 세트는 생성형 AI 로 초안을 만들고 사람이 검수한다. 원본은 커밋하지 않는다
- 지표 정의와 채점 형식은 [api-contract.md](../architecture/api-contract.md)
